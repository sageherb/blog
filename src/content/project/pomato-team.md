## 개요

Pomato는 `Lofi 음악`, `뽀모도로 타이머`, `소셜 커뮤니티`를 결합한 웹 플랫폼입니다.

데브코스 두 번째 팀 프로젝트로 진행했으며, 필수 요구 사항이었던 회원, 게시글 CRUD, 댓글, 좋아요 기능을 기반으로 커뮤니티 서비스를 구현했습니다. 여기에 Lofi 감성과 뽀모도로 사용 경험을 결합해 단순한 CRUD 프로젝트가 아니라, 사용자가 음악을 들으며 집중하고 커뮤니티와 상호작용할 수 있는 서비스 경험을 목표로 했습니다.

팀은 프론트엔드 개발자 3명으로 구성되었고, 별도의 디자이너 없이 기획, UI/UX 설계, 디자인 시스템 구성, 구현까지 모두 직접 진행했습니다.

- `Supabase` 기반 데이터베이스 스키마 설계
- Google, Kakao, GitHub Supabase 기반 OAuth 로그인 구현
- Button, Toast 등 공통 컴포넌트 구현
- 메인 페이지의 뽀모도로 타이머, 음악 재생 UI, 애니메이션 구현
- 정보 수정 페이지 구현
- `Figma Make AI`를 활용한 UI/UX 설계 및 디자인 시스템 구성
- `cva` 기반 `variants` 설계
- Glassmorphism 스타일의 UI 디자인

## 문제 정의

이번 프로젝트의 핵심은 기능 구현 자체보다도, 주어진 요구 사항을 어떤 서비스 경험으로 풀어낼 것인가에 있었습니다.

필수 요구 사항은 회원, 게시글 CRUD, 댓글, 좋아요처럼 일반적인 소셜 커뮤니티 기능이었지만, 그대로 구현하면 흔한 게시판 프로젝트에 머무를 가능성이 컸습니다. 그래서 팀에서는 커뮤니티 기능을 유지하면서도 프로젝트만의 명확한 콘셉트를 만들기 위해 `Lofi 뽀모도로 소셜 커뮤니티`라는 주제를 선택했습니다.

이 주제에는 두 가지 문제가 있었습니다.

첫 번째는 Lofi와 뽀모도로의 감성을 살릴 수 있는 UI/UX가 필요하다는 점이었습니다. Lofi는 기능보다 분위기와 몰입감이 중요한 장르이기 때문에, 단순한 입력 폼과 리스트 중심의 화면만으로는 서비스의 성격을 드러내기 어려웠습니다.

두 번째는 커뮤니티 기능과 뽀모도로 타이머가 서로 충돌하지 않도록 화면 구조를 설계해야 한다는 점이었습니다. 뽀모도로는 집중을 돕는 기능이고, 커뮤니티는 사용자의 시선을 분산시킬 수 있는 기능입니다. 따라서 두 기능을 한 화면에 넣되, 사용자가 원할 때만 커뮤니티 영역에 접근할 수 있는 구조가 필요했습니다.

## UI/UX 설계

초기에는 뽀모도로와 음악 재생 경험을 메인에 두고, 커뮤니티 기능은 화면 오른쪽의 접었다 펼 수 있는 반투명 패널에 배치하는 방향으로 설계했습니다.

이 구조를 선택한 이유는 명확했습니다.

사용자가 집중할 때는 타이머와 음악에만 몰입하고, 필요할 때만 패널을 열어 게시글이나 댓글을 확인할 수 있게 만들기 위해서였습니다. 즉, 커뮤니티 기능을 완전히 숨기지는 않되, 집중 경험을 방해하지 않는 보조 영역으로 분리하고자 했습니다.

당시 팀원 모두 디자인 경험이 많지 않았고, 저 역시 `Figma`가 처음이었기 때문에 초기에는 손으로 직접 UI 구조를 그려가며 논의했습니다. 이후 `Figma Make AI`를 활용해 빠르게 프로토타입을 만들고, 팀원들과 화면 구조와 분위기를 검토했습니다.

이 과정에서 단순히 AI 결과물을 그대로 사용한 것이 아니라, 서비스 콘셉트에 맞는 구조를 찾기 위한 탐색 도구로 활용했습니다. 빠르게 여러 시안을 확인하면서 팀의 의사결정 속도를 높였고, 이후에는 선택한 방향을 바탕으로 세부 디자인과 컴포넌트 구조를 정리했습니다.

## Glassmorphism과 디자인 시스템

Pomato의 시각적 방향성은 `Glassmorphism`에 가깝게 잡았습니다.

Lofi 서비스 특유의 차분하고 몽환적인 분위기를 살리기 위해 반투명한 패널, 어두운 배경, 은은한 입체감을 활용했습니다. 다만 Glassmorphism은 `blur`, 그림자, gradient border 같은 효과를 많이 사용하기 때문에 성능 부담이 생길 수 있다고 판단했습니다.

그래서 모든 요소에 강한 blur를 적용하기보다는, 핵심적인 레이어와 분위기를 만드는 영역에만 제한적으로 사용했습니다. border gradient와 과한 shadow는 줄이고, 투명도와 배경 대비를 중심으로 frosted glass에 가까운 느낌을 구현했습니다.

또한 Figma 커뮤니티의 UI Kit들을 참고하며, 디자인을 단순히 화면 단위로 만드는 것이 아니라 컴포넌트와 상태 단위로 관리해야 한다는 점을 배웠습니다.

이 경험은 이후 구현 방식에도 영향을 주었습니다.

디자인 단계에서는 UI Kit와 variants를 기준으로 정리하고, 구현 단계에서는 컴포넌트 variants와 디자인 토큰을 활용해 일관성을 유지하려고 했습니다. 이 프로젝트를 통해 디자인 시스템이 단순히 예쁜 화면을 만들기 위한 도구가 아니라, 팀 단위 개발에서 속도와 일관성을 동시에 확보하기 위한 구조라는 것을 체감했습니다.

## 공통 컴포넌트와 variants 설계

제가 맡은 공통 컴포넌트 중 가장 고민이 많았던 부분은 `Button` 컴포넌트였습니다.

버튼은 단순해 보이지만 실제 프로젝트에서는 다음과 같은 조건들이 함께 존재했습니다.

- 다크 모드와 라이트 모드
- 아이콘만 있는 버튼과 텍스트가 함께 있는 버튼
- 원형 버튼과 둥근 사각형 버튼
- 페이지별로 다른 시각적 스타일
- 여러 크기와 상태

처음에는 `twMerge`를 이용해 조건부 class를 병합하는 방식으로 구현하려 했지만, 조건이 늘어날수록 분기 구조가 복잡해졌습니다. 단순 문자열 조합으로 관리하면 이후 스타일을 수정하거나 새로운 variant를 추가할 때 유지보수성이 떨어질 수 있다고 판단했습니다.

그래서 `Class Variance Authority(cva)`를 도입해 variant 중심으로 Button 스타일을 관리했습니다.

이 방식은 단순히 코드를 깔끔하게 만들기 위한 선택이 아니라, 디자인 시스템과 구현 컴포넌트 사이의 대응 관계를 명확히 만들기 위한 선택이었습니다. Figma에서 정리한 버튼의 형태와 상태를 코드에서도 variant로 표현하면, 스타일 변경과 확장이 훨씬 예측 가능해졌습니다.

이후 다른 공통 컴포넌트에도 같은 방향을 공유했고, 팀원들도 각자 맡은 컴포넌트에 variants 기반 스타일링을 적용했습니다.

## Supabase와 인증 구현

프로젝트에서는 `Supabase`를 이용해 데이터베이스, 인증, OAuth 로그인을 구현했습니다.

저는 데이터베이스 스키마 설계와 전체적인 Supabase 설정을 담당했습니다. 게시글, 댓글, 좋아요, 사용자 정보 등 커뮤니티 기능에 필요한 테이블 구조를 설계하고, 각 기능이 어떤 관계를 가져야 하는지 정리했습니다.

처음 어려웠던 부분은 `RLS(Row Level Security)`였습니다.

처음에는 사용자별 CRUD 권한이 별도로 관리된다는 점을 깊게 인식하지 못했고, 기능 구현 중 권한 문제로 요청이 실패하는 상황을 겪었습니다. 이후 Supabase의 RLS 정책을 다시 확인하면서, 사용자가 자신의 데이터만 수정하거나 삭제할 수 있도록 정책을 점검했습니다.

OAuth 로그인은 Google, Kakao, GitHub를 지원하도록 구현했습니다. Supabase가 제공하는 추상화된 인증 메서드와 공식 문서를 활용해 로그인 흐름을 구성했고, 각 플랫폼에서 제공하는 사용자 정보를 프로젝트의 사용자 테이블 구조에 맞게 가공하는 방식도 함께 설계했습니다.

이 과정에서 인증 기능은 단순히 로그인 버튼을 붙이는 문제가 아니라, 외부 provider에서 받은 사용자 정보를 서비스 내부 모델과 어떻게 연결할지까지 고려해야 한다는 점을 배웠습니다.

다만 OAuth와 인증/인가 영역은 추상화된 도구에 의존하면 내부 동작을 놓치기 쉽다고 느꼈습니다. 그래서 이 프로젝트 이후에도 session, cookie, token, authorization flow에 대한 이해를 더 깊게 가져가야 한다고 판단했습니다.

## 메인 페이지와 인터랙션

Pomato의 메인 페이지에서는 뽀모도로 타이머, 음악 재생, 시각적 애니메이션을 구현했습니다.

처음부터 음악 기능을 계획했던 것은 아니지만, 프로젝트 후반에 서비스 완성도를 높이기 위해 추가했습니다. 다만 음악 재생 버튼과 타이머 재생 버튼이 별도로 존재하면 사용자가 어떤 버튼을 눌러야 하는지 혼란스러울 수 있다고 판단했습니다.

그래서 타이머 숫자를 음악 재생 바처럼 보이도록 디자인하고, 재생 흐름의 중심을 뽀모도로 타이머에 두었습니다. 음악 재생과 정지는 레코드 판 클릭 이벤트로 처리했고, 음악이 재생 중이라는 상태는 레코드 판 회전과 비주얼 이퀄라이저 애니메이션으로 표현했습니다.

또한 Lofi 분위기를 강화하기 위해 배경에는 비가 내리는 rain effect를 추가했습니다.

다만 애니메이션을 많이 넣는 것이 항상 좋은 UX로 이어진다고 보지는 않았습니다. 사용자가 콘텐츠를 읽거나 조작해야 하는 커뮤니티 패널에는 과한 모션을 줄이고, 버튼 인터랙션과 화면 전환 duration 정도만 적용했습니다.

반대로 음악, 레코드 판, 배경 효과처럼 서비스의 감성을 만드는 요소에는 애니메이션을 적극적으로 적용했습니다.

즉, 모든 요소를 화려하게 만드는 것이 아니라, 사용자의 집중과 조작을 방해하지 않는 선에서 서비스의 분위기를 강화하는 방향으로 Motion을 사용했습니다.

## 아키텍처와 구조에 대한 고민

이 프로젝트에서는 폴더 구조와 컴포넌트 분리에도 신경을 많이 썼습니다.

당시 `FSD(Feature-Sliced Design)`를 처음 공부하고 일부 도입했으며, 전체적인 컴포넌트 구조는 아토믹 패턴을 참고해 설계했습니다. 공통 컴포넌트와 기능 단위 컴포넌트를 구분하고, 페이지별 책임이 지나치게 커지지 않도록 나누려고 했습니다.

다만 프로젝트를 진행하면서 작은 규모의 프로젝트에서는 구조화 자체가 오히려 복잡도를 높일 수 있다는 점도 느꼈습니다.

아키텍처는 정답처럼 도입하는 것이 아니라, 프로젝트 규모, 팀원 수, 기능 복잡도, 유지보수 기간에 따라 선택해야 한다는 기준을 갖게 되었습니다. 이 경험은 이후 프로젝트에서 특정 패턴을 무조건 적용하기보다, 현재 문제에 맞는 구조인지 먼저 판단하게 만든 계기가 되었습니다.

## 협업과 코드 리뷰

팀 인원이 3명으로 다른 팀보다 적었기 때문에 각자가 맡아야 하는 범위가 넓었습니다. 저는 기능 구현뿐 아니라 기획, UI/UX 설계, 디자인 시스템 정리, Supabase 설정까지 여러 영역을 함께 담당했습니다.

이 과정에서 코드 리뷰의 중요성도 크게 느꼈습니다.

단순히 PR을 승인하기 위한 리뷰가 아니라, 팀원의 코드를 꼼꼼히 읽으면서 실제 버그를 발견한 경험이 있었습니다. 이때 코드 리뷰가 단순한 형식적 절차가 아니라, 팀 전체의 품질을 높이는 실질적인 과정이라는 것을 체감했습니다.

또한 디자인과 구현이 분리되어 있지 않은 팀 환경에서는, 컴포넌트 구조나 variants 설계 같은 기술적 결정이 디자인 일관성과도 직접 연결된다는 점을 배웠습니다.

## 결과 및 배운 점

Pomato는 제게 UI/UX, 디자인 시스템, 인증, 데이터베이스, 컴포넌트 설계를 한 번에 경험하게 해준 프로젝트였습니다.

특히 의미 있었던 부분은 단순히 새로운 기술을 사용했다는 점이 아니라, 각 기술을 왜 사용했고 어떤 문제를 해결하기 위해 도입했는지를 고민했다는 점입니다.

- `Figma Make AI`는 빠른 시안 탐색과 팀 내 의사결정을 위해 사용했습니다.
- `Glassmorphism`은 서비스 분위기를 살리되, 성능 부담을 고려해 제한적으로 적용했습니다.
- `cva`는 복잡한 Button 스타일 조건을 variant 중심으로 관리하기 위해 도입했습니다.
- `Supabase`는 빠른 백엔드 구성을 가능하게 했지만, RLS와 인증/인가의 개념적 중요성도 함께 체감했습니다.
- `Motion`은 모든 요소에 적용하기보다, 서비스 감성과 사용자 경험에 기여하는 요소에 집중적으로 사용했습니다.

이 프로젝트를 통해 좋은 프론트엔드 개발은 화면을 구현하는 것에서 끝나지 않는다는 것을 배웠습니다.

사용자의 흐름을 고려해 UI를 배치하고, 디자인 시스템과 컴포넌트 구조를 연결하며, 인증과 데이터 모델이 서비스 요구 사항과 맞는지 검토하는 과정까지 모두 프론트엔드 개발자가 이해해야 할 영역이라고 느꼈습니다.

Pomato는 작은 팀 프로젝트였지만, 저에게는 “기능 구현자”에서 한 단계 더 나아가 제품의 구조와 경험을 함께 고민하는 개발자로 성장하게 만든 프로젝트였습니다.
